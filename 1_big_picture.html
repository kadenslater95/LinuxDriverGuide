The purpose of the Big Picture is to get you familiar with the common patterns across all device repos so that you can start wrapping your head around already existing driver code, sooner rather than later.
Because there are loads of different kinds of devices, device driver programming is structured in a way that makes code as clean as possible.
The highlights of how this is done are:
  • Inversion of Control
  • Operations Table
Inversion of Control The kernel is the running program. It just calls functions that have "standard" names when it wants input/output from your device. e.g. When a device goes to sleep it will check if you have specified a `sleep` function and call it. Similarly, it checks for a `resume` function when it wakes up. More on these functions in the Operations Table.
Operations Table The word table is used loosely, its just what they call it. The methods I was mentioning about sleep and resume are put on a `struct dev_pm_ops` as a `sleep` and ...


There is a struct for each class of situations, e.g. power management, character I/O, block I/O, network socket I/O...
